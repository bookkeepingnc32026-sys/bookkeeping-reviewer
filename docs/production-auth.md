# Production email confirmation and recovery

Public website: **https://bookkeeping-reviewer-2xwo.vercel.app**

There are two independent settings: the URL generated by this Next.js application, and the URLs/templates allowed by hosted Supabase Auth. A GitHub push updates source code; it does not update your Supabase dashboard settings or Vercel environment variables.

## 1. Set the public URL in Vercel

Open your `bookkeeping-reviewer` Vercel project, then **Settings → Environment Variables**. Set this for the **Production** environment:

```dotenv
NEXT_PUBLIC_APP_URL=https://bookkeeping-reviewer-2xwo.vercel.app
```

Keep the existing `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` values. The Supabase URL must be its project origin without `/rest/v1/`.

Save, then redeploy the latest production source from **Deployments → Redeploy**. If Git deployment integration is enabled, pushing to its production branch also creates a new deployment. Environment-variable changes apply to a new deployment, not an already running deployment.

The application prefers the configured public HTTPS origin. On Vercel, `VERCEL_PROJECT_PRODUCTION_URL` is a fallback if an old localhost value was accidentally copied to production. Keep Vercel's automatic system environment variables enabled. Other production hosts must configure the public URL explicitly. Production account emails cannot fall back to localhost, private network addresses, or untrusted forwarded headers.

## 2. Configure Supabase URLs

Open the project's [Authentication → URL Configuration](https://supabase.com/dashboard/project/iflxbxabttbmgnqscvwh/auth/url-configuration).

Set **Site URL** to:

```text
https://bookkeeping-reviewer-2xwo.vercel.app
```

Add both of these **Redirect URLs** and save:

```text
https://bookkeeping-reviewer-2xwo.vercel.app/auth/callback
https://bookkeeping-reviewer-2xwo.vercel.app/auth/callback?next=/reset-password
```

Local callback URLs may remain for isolated developer tests, but the shared project's Site URL must stay on the public website. Keep email confirmation enabled.

## 3. Apply the server-side email templates

Open **Authentication → Email → Templates** (the dashboard may label this area **Email Templates**). Replace the relevant email bodies with the matching repository files:

| Supabase template    | Repository file                        |
| -------------------- | -------------------------------------- |
| Confirm signup       | `supabase/templates/confirmation.html` |
| Reset password       | `supabase/templates/recovery.html`     |
| Change email address | `supabase/templates/email-change.html` |

Save each template. The signup and email-change templates use `{{ .RedirectTo }}`, which the app sets to the complete public callback URL. Do not append another `/auth/callback` to this variable. The recovery template uses `{{ .SiteURL }}` followed by the callback path.

These templates send `token_hash` and the verification type to the server callback. Unlike legacy PKCE code links, this verification does not depend on a code-verifier cookie in the browser where signup started. It therefore supports opening a signup confirmation on another device or browser. Existing PKCE links remain supported when their original verifier cookie is available.

## 4. Use a newly generated email

Previously delivered messages retain their old links. After the new deployment and settings are active:

1. Open https://bookkeeping-reviewer-2xwo.vercel.app/resend-confirmation.
2. Enter the email address of your existing unconfirmed account and request a fresh link.
3. Open the **newest** message and select **Confirm email address**.
4. Verify that the destination begins with `https://bookkeeping-reviewer-2xwo.vercel.app/auth/callback`, with no `localhost` hostname.
5. After verification, a learner is directed to the learner portal. Invalid/expired links display recovery guidance and a resend option.

Test the same flow with signup on one browser and the new token-hash email opened on another. Test password recovery from **Forgot password** as well. Use accounts and inboxes you control. Test email links once; verification tokens are single-use. Successful signup, SMTP delivery, and cross-device sign-in cannot be verified solely by an application build or unit test.

## 5. Enable email delivery for real learners

Supabase's built-in test mailer restricts delivery to project-team addresses and is not intended for production. To send confirmations to arbitrary learner email addresses, configure your own SMTP service under Supabase's email settings. Keep SMTP credentials in Supabase's secure configuration; this application does not need them in its source code. No SMTP subscription or provider account is created automatically by this change.

### Delivery failures and duplicate registrations

A successful signup response does not prove inbox delivery. Supabase can also conceal an existing account behind a generic signup response. Check the Auth account and email-provider logs rather than repeatedly submitting signup or deleting profile rows.

The API returns HTTP 429 and `email_rate_limited` when Supabase reports its email-sending limit. It returns HTTP 503 and `email_delivery_unavailable` when the configured mailer cannot send to a recipient. Both are failures, not confirmation-email success responses. Configure production SMTP and its sending limits before opening registration to learners; changing Next.js code or disabling Vercel protection cannot raise the mailer's quota.

Also inspect the actual confirmation email's destination. If Supabase rejects the application's requested callback because it is missing from the redirect allow-list, the message can use the configured Site URL instead. An old Site URL such as `https://bookkeeping-reviewer-bookkeeping2.vercel.app` can therefore keep sending learners to a different deployment. Update the Site URL and allow-list above, apply the templates, and request a new email. Keep any older deployment addresses referenced by delivered emails publicly reachable while replacing those links.

## Technical checks

```powershell
npm test
npm run typecheck
npm run build
```

The regression tests cover canonical public URLs behind internal proxy addresses, Vercel fallback, loopback rejection, local development, token-hash confirmation without a verifier cookie, recovery routing, expired tokens, and unsafe redirect targets. They use test doubles and do not send real emails.
